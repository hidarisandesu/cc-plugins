# CONTEXT.md フォーマット

## 構造

```md
# {コンテキスト名}

{このコンテキストが何であり、なぜ存在するのかを1～2文で説明する。}

## 用語

**注文**:
{用語を1～2文で説明する}
_避けるべき語_: 購入、取引

**請求書**:
納品後に顧客へ送付する、支払いを求める文書。
_避けるべき語_: 請求、支払依頼

**顧客**:
注文を行う個人または組織。
_避けるべき語_: クライアント、購入者、アカウント
```

## ルール

- **明確な意見を持つ。** 同じ概念を表す言葉が複数ある場合は、最も適切な言葉を選び、他の言葉は `_避けるべき語_` の下に列挙する。
- **定義は簡潔にする。** 最大でも1～2文で記述する。それが何であるかを定義するのであって、それが何をするかを定義するのではない。
- **このプロジェクトのコンテキストに固有の用語のみを含める。** 一般的なプログラミング概念（タイムアウト、エラーの種類、ユーティリティパターンなど）は、プロジェクトで広く使用されている場合でも含めない。用語を追加する前に、これはこのコンテキストに固有の概念か、それとも一般的なプログラミング概念かを自問する。前者のみ含める。
- 自然なグループ分けが見られる場合は、**用語を小見出しの下にグループ化する。** すべての用語が単一のまとまった領域に属する場合は、フラットなリストでも構わない。

## シングルコンテキストとマルチコンテキストのリポジトリ

**シングルコンテキスト（ほとんどのリポジトリ）：** リポジトリのルートに `CONTEXT.md` ファイルが 1 つだけある。

**複数のコンテキスト:** リポジトリのルートにある `CONTEXT-MAP.md` に、コンテキスト、その場所、および相互の関係が一覧表示されている。

```md
# コンテキストマップ

## コンテキスト

- [Ordering](./src/ordering/CONTEXT.md) — 顧客からの注文を受け付け、追跡します
- [Billing](./src/billing/CONTEXT.md) — 請求書を作成し、支払いを処理します
- [Fulfillment](./src/fulfillment/CONTEXT.md) — 倉庫でのピッキングと出荷を管理します

## 関係性

- **Ordering → Fulfillment**: Ordering は `OrderPlaced` イベントを発行します。Fulfillment はこれらのイベントを消費してピッキングを開始します
- **Fulfillment → Billing**: Fulfillment は `ShipmentDispatched` イベントを発行します。Billing は請求書生成のためにこれらを使用します
- **Ordering ↔ Billing**: `CustomerId` と `Money` の共有型
```

このスキルは、適用される構造を推論する。

- `CONTEXT-MAP.md` が存在する場合、それを読み込んでコンテキストを特定する
- ルート `CONTEXT.md` のみが存在する場合、単一のコンテキストを使用する
- どちらも存在しない場合、最初の用語が解決されたときにルート `CONTEXT.md` を遅延的に作成する

複数のコンテキストが存在する場合、現在のトピックがどのコンテキストに関連しているかを推論する。不明な場合は、質問する。
