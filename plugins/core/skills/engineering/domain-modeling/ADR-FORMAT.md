# ADRフォーマット

ADRは`docs/adr/`ディレクトリに保存され、`0001-slug.md`、`0002-slug.md`、といったように連番で命名される。

`docs/adr/`ディレクトリは、最初のADRが必要になった時のみ、必要に応じて作成される。

## テンプレート

```md
# {決定の短いタイトル}

{1～3文：背景、決定内容、そしてその理由}
```

以上である。ADRは1つの段落で構成できる。重要なのは、*決定がなされたこと*、そして *その理由* を記録することであり、各項目を埋めることではない。

## オプションのセクション

これらの項目は、真に価値のある場合にのみ含める。ほとんどのADRでは不要である。

- **ステータス** フロントマター（`proposed | accepted | deprecated | superseded by ADR-NNNN`） — 決定事項を再検討する際に役立つ
- **検討されたオプション** — 却下された代替案を記憶しておく必要がある場合にのみ使用する
- **結果** — 明らかでない下流への影響を指摘する必要がある場合にのみ使用する

## 番号付け

`docs/adr/` をスキャンして、既存の最大番号を探し、1 増やす。

## ADR を提案するタイミング

以下の 3 つの条件がすべて満たされている必要がある。

1. **覆すのが困難である** — 後から方針を変更する場合、そのコストが無視できないほど大きい。
2. **背景を知らないと不可解に思える** — 将来の読者がコードを見て「なぜこんなやり方をしたのだろう？」と疑問に思うようなものである。
3. **明確なトレードオフの結果である** — 実際に複数の選択肢が存在し、特定の理由に基づいてその中の一つを選んだものである。

容易に覆せる決定なら、わざわざ記録に残す必要はない。どうせ後で覆すことになるからだ。また、意外性のない決定であれば、誰もその理由を疑問に思うことはないだろう。現実的な代替案が存在しなかった場合も、「当然の選択をした」という以上のことを記録する必要はない。

### 条件

- **アーキテクチャの構成。** 「モノレポを使用しています。」「書き込みモデルはイベントソーシングで、読み取りモデルはPostgresに投影されています。」
- **コンテキスト間の統合パターン。** 「注文と請求は、同期HTTPではなく、ドメインイベントを介して通信します。」
- **ベンダーロックインにつながる技術選択。** データベース、メッセージバス、認証プロバイダ、デプロイメントターゲット。すべてのライブラリではなく、差し替えに四半期かかるようなものだけを対象とする。
- **境界とスコープの決定。** 「顧客データは顧客コンテキストが所有し、他のコンテキストはIDのみで参照します。」明確な「いいえ」は、「はい」と同じくらい価値がある。
- **当然の道からの意図的な逸脱。** 「Xという理由で、ORMではなく手動SQLを使用しています。」常識的な読者が正反対のことを想定するような記述はすべて、記録しておくべきである。こうした記述は、次のエンジニアが意図的な変更を「修正」してしまうことを防ぐ。
- **コードに表れていない制約。** 「コンプライアンス要件のため、AWSは使用できません。」「パートナーAPIとの契約により、応答時間は200ms未満でなければなりません。」
- **却下理由が明白でない代替案。** GraphQLを検討したものの、微妙な理由でRESTを選択したのであれば、それを記録しておくべきである。そうしないと、半年後に誰かが再びGraphQLを提案してくるかもしれない。
