# ドメインモデリング

設計を行う中で、プロジェクトのドメインモデルを積極的に構築し、洗練させていきます。これは *能動的* な実践を伴うスキルです。用語に疑問を投げかけ、エッジケース（境界条件）のシナリオを考案し、用語集や決定事項が明確になった瞬間にそれを書き留めることが求められます。（単に語彙を確認するために `CONTEXT.md` を *読む* だけでは、このスキルを発揮したことにはなりません。それはどんなスキルでも行える単純な作業に過ぎません。このスキルは、モデルを参照するだけでなく、モデルそのものを変更する際に必要となるものです。）

## ファイル構造

多くのリポジトリは単一のコンテキストを持ちます：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートディレクトリに `CONTEXT-MAP.md` が存在する場合、そのリポジトリは複数のコンテキストを持っています。このマップは各コンテキストの場所を示しています：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← システム全体に及ぶ決定
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← コンテキスト固有の決定
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは必要に応じて（遅延的に）作成します。つまり、実際に書き込む内容がある場合にのみ作成します。`CONTEXT.md` が存在しない場合は、最初の用語が確定した時点で作成します。`docs/adr/` ディレクトリが存在しない場合は、最初の ADR（アーキテクチャ決定記録）が必要になった時点で作成します。

## セッション中

### 用語集との整合性を問う

ユーザーが `CONTEXT.md` にある既存の用語と矛盾する言葉を使った場合は、即座に指摘してください。「用語集では『cancellation（キャンセル）』を X と定義していますが、あなたは Y という意味で使っているようです。どちらが正しいのでしょうか？」

### 曖昧な表現を明確にする

ユーザーが曖昧な用語や、複数の意味を持つ用語（オーバーロードされた用語）を使った場合は、正確で標準的な用語を提案してください。「『account（アカウント）』とおっしゃいましたが、それは『Customer（顧客）』のことですか、それとも『User（ユーザー）』のことですか？ それらは異なる概念です。」

### 具体的なシナリオを議論する

ドメイン内の関係性について議論する際は、具体的なシナリオを用いてその妥当性を検証（ストレステスト）してください。エッジケースを突くようなシナリオを考案し、概念間の境界についてユーザーに正確な定義を促してください。

### コードとの整合性を確認する

ユーザーがシステムの動作について説明した際は、コードがそれと一致しているかを確認してください。矛盾が見つかった場合はそれを指摘してください。「コード上では注文全体がキャンセルされるようになっていますが、先ほどは部分的なキャンセルも可能だと言いましたよね。どちらが正しいのでしょうか？」

### CONTEXT.md をその場で更新する

用語の意味や定義が確定した際は、その都度 `CONTEXT.md` を更新してください。変更を後でまとめて行うのではなく、確定したタイミングで記録します。記述には [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) のフォーマットを使用してください。

`CONTEXT.md` には実装の詳細は一切含めないでください。`CONTEXT.md` を仕様書やメモ書き、あるいは実装に関する意思決定の記録場所として扱わないようにしましょう。これはあくまで用語集であり、それ以外の何物でもありません。

### ADR の作成は慎重に

ADR（アーキテクチャ決定記録）の作成を提案するのは、以下の3つの条件すべてに当てはまる場合のみにしてください。

1. **覆すのが困難である** — 後から方針を変更する場合、そのコストが無視できないほど大きい。
2. **背景を知らないと不可解に思える** — 将来その内容を目にした人が「なぜこのような方法をとったのか？」と疑問に思うようなものである。
3. **明確なトレードオフの結果である** — 実際に複数の選択肢が存在し、特定の理由に基づいてその中の一つを選んだものである。

これら3つの条件のいずれか一つでも欠けている場合は、ADR を作成しないでください。記述には [ADR-FORMAT.md](./ADR-FORMAT.md) のフォーマットを使用してください。
